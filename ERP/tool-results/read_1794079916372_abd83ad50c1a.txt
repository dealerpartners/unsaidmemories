    15→## PART 1 — System Logic (the rules every module obeys)
    16→
    17→### 1.1 The five shared entities
    18→
    19→Everything in the Create Actions list collapses into five entity families. This is what makes the platform feel integrated: modules are *views* over shared entities, not separate databases.
    20→
    21→| Entity | What it is | Roles / Types | Used by |
    22→|---|---|---|---|
    23→| **Party** | One person/company record | Customer, Vendor, Supplier, Contractor, Seller, Lead (a party can hold many roles) | Sales, Expenses, CRM, Orders, Support, Tax (1099), Marketplace |
    24→| **Item** | Anything sellable/buyable | Product, Service, Blank, Bundle, Design-linked product, Gift card, Subscription | Catalog, Studio, Invoices, Bills, PO, Orders, Inventory, Channels |
    25→| **Document** | Any multi-line transaction | Invoice, Estimate, Sales order, Sales receipt, Credit memo, Bill, Expense, Check, PO, Vendor credit, RMA, Journal entry | Sales, Expenses, Orders, Purchasing, Returns, Accounting |
    26→| **Money movement** | Cash actually moving | Payment, Payment link, Deposit, Transfer, Settlement/Payout, Refund | Sales, Bills, Banking, Reconcile, Stripe/Shopify |
    27→| **Account** | Ledger node | Chart of Accounts, Bank, Credit card, Loan, Line of credit | Accounting, every Document line, Reconcile, Tax, Reports |
    28→
    29→**Rule:** "Add vendor" and "Add supplier" and "Add customer" are the **same drawer** (Party drawer) with a different default role pill. Same for "Add contractor" (role = Contractor, plus W-9 invite section). Never build four forms.
    30→
    31→**Rule:** Every Document is rendered by **one Document Engine** (header → lines → totals → attachments/memo → status → activity). Invoice, Bill, PO, Sales order, Estimate, Credit memo, Vendor credit differ only by *config* (party role, line columns, status machine, posting rules). Build once.

    33→### 1.2 Surface rules — which container for which job
    34→
    35→| Surface | Use when | Examples | Escape hatch |
    36→|---|---|---|---|
    37→| **Pill / popover (peek)** | Read-only glance, zero commitment | Hover a customer pill → balance, last order, open tickets | Click → open drawer; ⌘-click → new tab |
    38→| **Modal** | Single decision, ≤5 fields, result is immediate | Record payment, Void, Refund, Mark shipped, Adjust stock, Transfer, Send, Remind, Approve/Decline return, Archive | None (small by design) |
    39→| **Drawer (right, 480px; 720px wide mode)** | Create/edit a *record* while staying on the list | Party, Product, Account, Category, Task, Note, Ticket, Banner, Popup, Discount code, Collection | **Make full page** (already in your Bills create menu) |
    40→| **Document page (full)** | Multi-line transactions | Invoice, Bill, PO, Sales order, Estimate, Credit memo, Journal entry | Print/PDF/Email views as tabs inside the page |
    41→| **Workspace** | Many records, one batch outcome | Pay bills, Receive payment, Reconcile, Batch slips & labels, Cycle count, Upload multiple bills | Saves as draft batch |
    42→| **Studio** | Visual canvas | Design, Collection canvas, Product mockup | "Back to record" returns to originating drawer |
    43→| **Command palette (⌘K)** | Jump or create anywhere | "New invoice for Acme", "Bill from Printful" | Same Create menu, searchable |
    44→
    45→**Escalation ladder:** Peek → Modal → Drawer → Full page. A user can always promote upward without losing input (drawer → full page keeps state).

    47→### 1.3 The Context Envelope (this is the integration engine)
    48→
    49→Every surface carries an invisible envelope. Creating something from inside a record **prefills from that record**; creating from the global Create menu inherits only the **active tab's** envelope.
    50→
    51→```
    52→envelope = {
    53→  origin_module, origin_record_id, origin_tab_id,
    54→  party_id, order_id, item_id, design_id, account_id,
    55→  channel_id, currency, date_range, return_to
    56→}
    57→```
    58→
    59→Examples:
    60→- On **Order #1042** → Create → Invoice: party, lines, channel, and `order_id` are prefilled and linked.
    61→- On **Vendor: Printful** → Create → Bill: vendor, terms, default expense category prefilled; open POs from that vendor show as a "Match PO" suggestion.
    62→- On a **Design** in Studio → Create → Product: design attached, blank picker opens, margins pre-calculated from supplier cost.
    63→- On **Bank transaction** (Reconcile) → Create → Expense: amount, date, paid-from prefilled; "Match" and "Create" are siblings.
    64→
    65→`return_to` means closing any drawer/modal/page returns to the exact scroll position and tab it came from.

   141→### 1.9 Scoped Workspaces → Global Hubs (the Push pattern)
   142→
   143→Catalog, Contacts/CRM, Support and Marketing each exist **twice on purpose**: once as a **scoped view** inside the area where the work happens, and once as the **global hub** that is the system of record. This is how a user never has to leave what they're doing to get or create what they need.
   144→
   145→| Scoped view (where you work) | Lives in | Global hub (system of record) | Push action | Pull action |
   146→|---|---|---|---|---|
   147→| **My Catalog** | Design Studio / My products | **Global Catalog** | **Publish** | Add a blank/product from global into My Catalog |
   148→| **Contacts** | Finance (Sales, Expenses, Accounting) | **Global Contacts / CRM** | **Create and push** | **Search global → Use here** |
   149→| **Support** | Record context (Orders, Sales, Customers) | **Global Support** (Inbox & Tickets) | Create ticket here → lands in global queue | Link an existing global ticket |
   150→| **Marketing** | Studio / Catalog / Product context | **Global Marketing** | Promote here → lands in global calendar/queue | Pull from global library/campaigns |
   151→
   152→**Why two:** The designer cannot bounce to the global catalog mid-design. The user in Finance should not have to open CRM to bill someone. Scoped = fast, in context, only what you need. Global = governed, searchable, shared across the whole platform.
   153→
   154→**Rules**
   155→
   156→1. **One record identity.** A scoped view is a lens (or staging copy) linked to a single global ID. Pushing never makes a second record.
   157→2. **Two entry flows, same destination.**
   158→   - *Create → push:* new contact/product made in scope, then promoted to global.
   159→   - *Search → link:* user searches the global hub from the scoped view and attaches the existing record. Search always runs **before** create ("Does this already exist?").
   160→3. **Dedupe on push.** Match keys: Contact = email / tax ID / name + address; Product = SKU / design ID; Ticket = requester + related record. On a match the push modal offers **Link to existing · Merge · Create anyway**.
   161→4. **State pill on every scoped row:** `Local only` → `Pushed` → `Live/Global`. Catalog adds `Draft → Published → Syncing to channels`.
   162→5. **Provenance:** global records carry a source pill (`Created in Studio`, `Created in Finance`) so context is never lost after the push.
   163→6. **Visibility:** a scoped item is visible to the creator/team until pushed; global visibility follows Roles & permissions. Pushing is its own permission (e.g. Publish to catalog).
   164→7. **Edit from either view, with an "existing record" warning.** The user is never sent to the other view to make a change. Because there is only one record underneath (rule 1), an edit made in the scoped view or the global hub writes to the same record and shows up in both immediately. The safeguard is a warning on entering edit, not a redirect.
   165→
   166→   **Warning tiers (shown when edit opens, in the drawer/page header):**
   167→
   168→   | Tier | Applies to | What the user sees |
   169→   |---|---|---|
   170→   | **1 — Notice** | Local only / not yet pushed | No warning needed |
   171→   | **2 — Existing record banner** | Pushed/Global record, edited from anywhere | Banner: *"You're editing an existing record shared with Global Catalog."* + impact line (e.g. *Used in 14 products · 3 open invoices · 2 channels*) + **View where used**. Non-blocking. |
   172→   | **3 — Confirm on save** | Edit changes a field with downstream effect (price, SKU, email, tax ID, terms, default account) | Save opens a small modal with a before → after summary of what propagates; options **Save** · **Save and apply to open drafts** · Cancel |
   173→   | **4 — Locked** | Posted financial documents, reconciled transactions | Fields locked; offer **Void**, **Adjust**, or **Create credit memo** instead of edit |
   174→
   175→   **Safeguards that make edit-anywhere safe:**
   176→   - **Source pill in the activity log:** every edit records *edited from My Catalog / Studio / Finance / Global*, who, and the before → after values.
   177→   - **Concurrency:** soft lock banner (*"Maria is editing this"*) and a version check on save; on conflict show a field-level diff to keep mine, keep theirs, or merge.
   178→   - **Permissions still apply:** edit rights follow Roles and permissions; fields like cost, margin and bank details stay masked and read-only without the right role.
   179→   - **Undo:** a toast with **Undo** after save for Tier 2 edits, plus Activity → Restore previous value.
   180→   - **Same warning component everywhere:** one Existing Record Banner component, parameterized by record type and impact counts, used by Party, Item, Ticket, Campaign and Account drawers.
   181→8. **Create menu:** actions in a scoped context default to creating locally with **Push to global** pre-checked in the drawer footer (`Save` · `Save and push`).

   683→## PART 3.5 — Domain Structure & the Undefined Modules
   684→
   685→### A. The test: standalone module, sub-area, or setting?
   686→
   687→A thing earns its own **standalone module** only if it passes at least 4 of 5:
   688→
   689→1. Own primary entity with its own lifecycle
   690→2. Own list view people live in
   691→3. Own permission role (someone's job is this)
   692→4. Used by 3+ other modules
   693→5. Own ledger or compliance impact
   694→
   695→Otherwise it is a **sub-area** of a domain parent, or an **engine/setting** that other screens call.
   696→
   697→| Candidate | Entity | Own list | Own role | Used by | Ledger/compliance | Verdict |
   698→|---|---|---|---|---|---|---|
   699→| **Inventory** | Stock record + stock ledger | Yes | Warehouse/ops | Catalog, Orders, PO, Returns, Sales | Asset + COGS | **Standalone page** under Operations |
   700→| **Payroll** | Employee, Pay run, Pay stub | Yes | Payroll admin (restricted) | Accounting, Tax, Time, Reports | Heavy | **Standalone page** under People |
   701→| **Time** | Time entry | Weekly grid only | No | Payroll, Invoices, Tasks | Indirect | **Collapse** into People (feature, not a module) |
   702→| **Sales tax** | Rate, jurisdiction, filing | Filings only | Finance | Invoices, Orders, Items, Parties, Reports | Liability account | **Engine in Settings** + sub-area of Business Tax |
   703→
   704→### B. Catalog vs Inventory vs POD (the fix)
   705→
   706→Catalog, Inventory and Purchasing are three layers over the same Item, not three competing modules.
   707→
   708→| Layer | Question it answers | Owns |
   709→|---|---|---|
   710→| **Catalog** | *What is this and where is it sold?* | Definition, price, variants, **designs**, blanks, supplier link, channels, publish state |
   711→| **Inventory** | *What do I physically have?* | On hand, reserved, available, locations, cost layers, counts, transfers, adjustments, stock history |
   712→| **Purchasing** | *How does supply arrive?* | Purchase orders, receiving, supplier cost |
   713→
   714→Every Item gets a **Fulfillment type**, set in the Item drawer. It decides which tabs, pills and PO behavior the item has:
   715→
   716→| Fulfillment type | Example | Tracks stock? | Availability comes from | PO type | Pill |
   717→|---|---|---|---|---|---|
   718→| **Stock** | In-house goods, wholesale | **Yes** | Inventory on-hand | **Replenishment PO** (manual or reorder-point) | `42 in stock` |
   719→| **POD (print on demand)** | Design on a blank | No | Supplier / blank availability | **Fulfillment PO**, auto-created per order | `Made on demand` |
   720→| **Supplier-fulfilled (dropship)** | Supplier ships direct | No | Supplier feed | **Fulfillment PO**, auto-created per order | `Ships from supplier` |
   721→| **Digital / Service** | Download, hourly service | No | Always available | None | none |
   722→| **Bundle** | Tee + hat set | Derived | Lowest component availability | Per component | `Bundle` |
   723→
   724→**Consequences**
   725→- **Catalog owns POD completely:** Design → Product → Blank → Supplier. A POD product has no stock number, so the Inventory tab, Adjust stock and Cycle count never appear for it.
   726→- **Inventory is only for real stock.** Its list shows only items with *Track inventory = on*.
   727→- **Two PO types.** Replenishment PO is a manual or reorder-triggered buy for stock. Fulfillment PO is generated from an Order line and is linked to that order. Same Document Engine, different config.
   728→- **Blanks:** if the supplier holds them, a Blank is a Catalog record with supplier availability. If *you* buy and hold blanks (in-house printing), the Blank becomes an Inventory item (raw material), which later needs a simple production/BOM step. Flag this as a future decision.
   729→- **The stock pill on a product row** is replaced by the fulfillment pill for POD items.
   730→
   731→### C. Recommended domain parents
   732→
   733→Each parent is a nav group containing sub-areas. Each sub-area keeps its own list and Create actions.
   734→
   735→| Domain parent | Contains |
   736→|---|---|
   737→| **Finance** | Accounting · Sales · Expenses & Bills · **Business Tax** (Income tax · **Sales tax** · **Payroll tax** · 1099s) |
   738→| **People** | **Employees** · Contractors · **Time** · **Payroll** |
   739→| **Operations** | Orders · Fulfillment · Purchasing · **Inventory** · Returns · Shipping |
   740→| **Commerce** (Catalog & Design) | Studio + My Catalog → Global Catalog · Channels |
   741→| **Growth** | CRM · Marketing · Social · Ads |
   742→| **Support** | Inbox & Tickets · Queues · SLA · Trust & Safety |

   745→Notes on the moves:
   746→- **Contractors** are a People sub-area *and* keep a scoped view inside Expenses & Bills that pushes to People, the same pattern as section 1.9.
   747→- **Employees** are a Party role, so they use the same Party drawer with Pay, Tax and Bank sections (masked and restricted).
   748→- **Sales tax and Payroll tax** live under Business Tax because they are filings and liabilities, while the *engines* that feed them live elsewhere (Settings and Payroll).
   749→
   750→### D. Definitions for the four
   751→
   752→**Payroll** (People)
   753→- Entities: Employee (Party role), Pay schedule, Pay run, Pay stub, Tax forms (W-2, 941).
   754→- **Add employee:** Party drawer with Pay (salary/hourly, schedule), Tax (W-4, state), Bank (direct deposit), and an onboarding invite.
   755→- **Run payroll:** Workspace. Period → hours/salary (hours pulled from Time) → review gross / deductions / taxes / net → approve → pay.
   756→- Pay run list columns: Period · Pay date · Employees · Gross · Taxes · Net · Status pill (Draft / Approved / Paid) · ⋯
   757→- Posts journal entries automatically (wages expense, tax liabilities, bank). Rides along into Business Tax → Payroll tax and Reports.
   758→- **Decision to make:** build vs integrate. Payroll is compliance-heavy (filings, multi-state tax). Define the entity, surfaces and ledger posting now, and consider a provider integration behind the same screens.
   759→
   760→**Time** (People)
   761→- **Time entry:** modal or weekly grid. Fields: Person, Date, Hours, Related (Customer / Task / Order), Billable toggle, Rate, Note.
   762→- Rides along: Invoice has **Add billable time** on its line picker; Payroll pulls approved hours; Tasks can start a timer.
   763→
   764→**Sales tax** (Business Tax + Settings engine)
   765→- **Engine (Settings):** Rates and jurisdictions, tax categories, nexus rules.
   766→- **Item drawer:** Tax category field. **Party drawer:** Tax exempt toggle + certificate upload.
   767→- **Document Engine:** per-line tax calculation and a tax summary in the totals block.
   768→- **Business Tax → Sales tax:** liability by jurisdiction · Filing periods · **Pay sales tax** (workspace, like Pay bills) · Nexus alert pills.
   769→- Orders from channels arrive with marketplace-collected tax flagged, so it is excluded from your liability.
   770→
   771→**Inventory** (Operations)
   772→- Defined in Module: Purchasing & Inventory, now restricted to *Stock* items. Add: **Locations** (warehouses/bins) and a **Stock ledger** (every movement with source pill: PO receipt, order, adjustment, transfer, return).

   776→## PART 3.6 — POS, Gift Cards, Banking & Cards
   777→
   778→### A. POS (brick-and-mortar)
   779→
   780→**Principle:** POS is a **channel + a device surface**, not a separate system. A store sale is a normal Order/Sales receipt with a store channel pill, so Inventory, Accounting, CRM, Returns and Support all work unchanged.
   781→
   782→**Entities:** Location (store) · Register · Shift (drawer session) · Sale · Tender (card, cash, gift card, split) · Receipt · Hardware (reader, receipt printer, cash drawer, scanner)
   783→
   784→| Surface | Type | Contents |
   785→|---|---|---|
   786→| **POS app** | Full-screen, touch-first, offline-capable | Product grid + search + barcode scan → cart → attach customer (Party picker, optional, with `+ Add`) → discounts → tender → receipt (print/email/SMS) |
   787→| Open shift | Modal | Register, starting cash |
   788→| Close shift | Modal → count sheet | Counted cash vs expected, over/short, card totals, tips, **Z report** |
   789→| Cash in / out | Modal | Amount, reason (paid-out, petty cash) |
   790→| Park / resume sale | Inline | Held carts per register |
   791→| Refund / exchange | Modal | Scan or search receipt, select lines, restock toggle, refund to original tender or store credit |
   792→| Redeem / sell gift card | Modal | See 3.6 B |
   793→| Manager override | PIN modal | Required for discounts above threshold, voids, refunds, price override |
   794→
   795→**Back-office views:** Locations list (Name · Address · Registers · Open shift pill · Today's sales · Stock alerts) · Shifts list (Register · Cashier · Opened · Closed · Expected · Counted · Variance pill) · POS sales appear in Orders and Sales with a **Channel pill** `Store: Downtown`.
   796→
   797→**Rides along**
   798→- **Inventory:** stock is tracked per location; sales decrement the selling location; transfers between stores and warehouse; optional buy-online-pickup-in-store.
   799→- **POD items in store:** sold as an *order for later* (ship or pickup), never as instant stock.
   800→- **Accounting:** Z report posts a journal entry (sales by tender, tax, tips, cash over/short, gift card liability); card settlement reconciles to payouts in Bank transactions.
   801→- **Sales tax:** location-based rates and exemptions.
   802→- **CRM:** attached customer gets the sale on their profile; walk-up sales stay anonymous.
   803→- **Support:** receipt lookup creates a ticket or RMA with the sale pre-linked.
   804→- **Permissions:** Cashier, Shift lead, Manager roles; override rules live in Settings → Approvals and limits.
   805→- **Offline mode:** queue sales and card-present fallbacks, sync on reconnect, and define oversell conflict rules before launch.
   806→
   807→### B. Gift cards
   808→
   809→**Treat gift cards as your own ledger entity.** A gift card sale is a **liability**, not revenue; revenue is recognized when the card is redeemed.
   810→
   811→**Entities:** Gift card (code, initial value, balance, currency, issued to, expiry, status) · Gift card transaction (issue, redeem, reload, refund, adjust, expire)
   812→
   813→| Action | Surface | Notes |
   814→|---|---|---|
   815→| Sell gift card | Item type = Gift card (digital or physical) | Sold online, in POS, or on an invoice; card is created on payment |
   816→| Issue manually | **Drawer** | Amount, recipient, message, delivery (email / print), expiry |
   817→| Check balance | Popover / modal | Enter or scan code |
   818→| Redeem | Tender at checkout (online + POS) | Supports partial redemption and split tender |
   819→| Reload / Adjust / Disable | Modal | Reason required, logged |
   820→| Refund to gift card | Option in Refund modal | Or to store credit |
   821→
   822→**List columns:** ☐ · Code (masked) · Recipient · Purchaser (pill) · Issued · Initial · Balance · Expires · Status pill (Active / Partially used / Redeemed / Expired / Disabled) · Source (Online / Store / Manual) · ⋯
   823→**Right-click:** Open · Email card · Print · Reload · Adjust · **Create from this ▸** Ticket · Note · Disable
   824→**Detail:** Ledger of every movement with source pill (Order #, Register, Manual).
   825→**Accounting:** Gift card liability account; unredeemed-balance reports. Expiry, breakage and unclaimed-property rules vary by jurisdiction, so have a lawyer or accountant set the policy.
   826→**Store credit** (from credit memos and returns) uses the same ledger with a different type.
   827→
   828→### C. Banking & Cards (Stripe Connect + Treasury + Issuing)
   829→
   830→**Model:** Merchants are Connect connected accounts. Treasury for platforms provides a financial account per merchant; Issuing provides debit cards drawn on that account. Payouts from Stripe settle into the financial account.
   831→
   832→**Surfaces (Finance → Banking, merchant-facing)**
   833→
   834→| Surface | Type | Contents |
   835→|---|---|---|
   836→| Financial account | Page | Balance, available, pending, recent movement |
   837→| Move money | Modal | Transfer to / from linked bank, ACH out, payout sweep rules |
   838→| Cards list | List | Card · Holder (Party/Team pill) · Virtual/Physical · Status · Limit · Spent this period · ⋯ |
   839→| Issue card | **Drawer** | Holder, type, spend limit, allowed merchant categories, shipping, approval rules |
   840→| Card transactions | Feed in Bank transactions | Auto-create **Expense** with receipt-capture prompt; match to Bill; categorize via Rules |
   841→| Pay bills from financial account | Option in Pay bills workspace | Uses ACH details on the Vendor |
   842→| Onboarding / KYC-KYB | Drawer or embedded component | Collect and verify business info before enabling Banking |
   843→
   844→**Rides along:** Card spend limits tie to **Approvals and limits** · Settlement posts payouts into the financial account · Reconcile treats the financial account as a bank · Expenses and Business tax read card spend.
   845→
   846→**Compliance surfaces you must design (they land in Support):** a regulated **Complaints and Disputes queue** with recordkeeping, plus disclosures and customer-service access inside the Banking UI.

   850→## PART 3.7 — Support, Deepened
   851→
   852→Support is the module most likely to feel bolted on, so it is designed here as a **cross-module resolution layer**: an agent resolves the problem *from the ticket*, without leaving it.
   853→

   862→| **Internal** (optional) | Your team | Platform bugs, requests |

   865→

   881→
   882→- **Sources:** email, chat, social DMs, marketplace messages (Etsy, Amazon, etc.), web forms, **Report a problem… on an order**, POS receipt lookup, Banking complaint form.

   888→
   889→- **Help center / customer portal:** order status, tracking, self-serve returns (creates an RMA), past tickets, gift card balance. This is the deflection layer.

   891→- **CSAT:** survey on solve; QA review sampling.

   894→
   895→| Signal | Lands in |
   896→|---|---|

   907→## PART 4 — Gaps, Conflicts & Decisions to Make
   908→
   909→1. **Scoped vs global trees are intentional, not duplicates.** My Catalog (Studio) → Global Catalog, Contacts (Finance) → Global Contacts/CRM, plus scoped Support and Marketing, follow the Push pattern in section 1.9. Decided: edits are allowed from either view, with the existing-record warning (rule 7 in section 1.9). Still open: the dedupe keys, which role can push, and whether Orders is also scoped, since it appeared in both places.
   910→2. **"Not defined" items:** Payroll, Time, Inventory and Sales tax are now defined in Part 3.5 (domain placement, entities, surfaces). **Sales tax is still the build blocker**, since Invoices, Orders and Tax all depend on it. Payroll needs a build-vs-integrate decision. Blanks need a decision on whether you ever hold them yourself.
   911→3. **Product catalog prerequisite** (Department / Sub-department / Service type / SKU line). Make it inline-creatable so it never blocks entry; otherwise users will bounce.
   912→4. **Vendor vs Supplier vs Seller.** Recommended: **Vendor** = you pay them for operating costs; **Supplier** = fulfills your products (feeds PO, blanks, integrations); **Seller** = marketplace participant who sells through you. All Party roles, different drawer sections.
   913→5. **Order vs Sales order vs Invoice.** Recommend: Order is the commerce record (from channels); Sales order is manual order entry that becomes an Order; Invoice is the billing doc generated from either. Link all three with relation pills.
   914→6. **Statement ≠ Statement (bank).** Customer Statement (billing summary) and Reconcile "statement ending balance" use the same word. Label the latter "Bank statement."
   915→7. **Void vs Delete vs Archive.** Posted documents: **Void** only (keeps audit trail). Drafts: Delete. Parties/Items/Accounts: Archive.
   916→8. **Typos in source:** "Toytal Amount" → Total amount, "Announcemnets" → Announcements.
   917→9. **Workspace appears as an item** at the end of Support reports and Settings — probably a stray; confirm.
   918→
   919→**Enterprise-readiness gaps (cross-cutting, not yet specified):**
   920→
   921→| # | Area | What to define |
   922→|---|---|---|

   924→| 11 | **Event layer and API** | Every state change emits an event (`invoice.paid`, `order.shipped`, `ticket.sla_breached`) that powers Automations, notifications and integrations; webhooks with **idempotency keys** for payments and Stripe events |

   986→## 1. Architecture
   987→
   988→```
   989→AppShell
   990→ ├─ TabBar (each tab = { route, surfaceStack[], envelope })
   991→ ├─ SideNav (counts, pinned)
   992→ ├─ GlobalSearch / CommandPalette
   993→ ├─ CreateMenu (context-filtered)
   994→ ├─ Routed content (module page: TableShell / DocumentEngine / Workspace / Studio)
   995→ └─ SurfaceHost (renders the active tab's surface stack: drawer, modal, popover)
   996→```
   997→
   998→**Three central stores** (everything else is local state):
   999→
  1000→| Store | Holds | Key methods |
  1001→|---|---|---|
  1002→| `useSurfaces` | Per-tab surface stack, dirty flags | `open(request)`, `close(instanceId)`, `replace()`, `closeAll(tabId)`, `confirmDiscard()` |
  1003→| `useEnvelope` | Active tab's context envelope | `current()`, `derive(record)` returns the envelope for "Create from this" |
  1004→| `usePermissions` | Roles, field masks, feature flags | `can(action, record?)`, `isMasked(field)`, `flag(name)` |
  1005→
  1006→**Server state:** one query cache (React Query/SWR style), keyed `[entity, id]` and `[entity, 'list', normalizedQuery]`. Mutations invalidate by entity and by `relations` (so a payment refreshes the invoice, customer balance, bank feed and dashboard tile).
  1007→
  1008→**Rule: the server decides actions and permissions.** Menus, create menu and field masks come from the API (`/actions`, `/create-menu`, `meta.can`, `maskedFields`). The client never re-implements permission or state-machine logic. That is what keeps right-click menus identical everywhere.

  1094→## 3. Interaction Contract (click and unclick)
  1095→
  1096→### 3.1 Gesture table
  1097→
  1098→| Gesture | Target | Behavior |
  1099→|---|---|---|
  1100→| **Click** | Row body (record list) | Open record in **drawer** (replaces current drawer; dirty guard first) |
  1101→| **Click** | Row body (document list) | Navigate to **DocumentPage** |
  1102→| **Click** | Row checkbox | Toggle selection only; never opens |
  1103→| **Shift-click** | Checkbox | Range select |
  1104→| **Click** | Header checkbox | Select all visible; banner offers "Select all N matching" |
  1105→| **Click** | Empty table area / **Esc** | Clear selection (the "unclick") |
  1106→| **Click** | Pill | `PeekPopover` opens; click again or outside closes |
  1107→| **Hover** | Pill (desktop) | Peek after 300 ms intent delay; cancels on leave |
  1108→| **⌘/Ctrl-click** | Pill or row | Open in new tab (new envelope from source) |
  1109→| **Right-click** | Row | Context menu at cursor. If row is not selected, select **only** it. If row is within a selection, menu acts on the whole selection and shows bulk variants |
  1110→| **Click** | Menu item | Runs `surface` or `request`; `confirm` shows `ConfirmDialog` first; menu closes |
  1111→| **Click outside** | Menu / popover | Closes it |
  1112→| **Click outside** | Drawer | **Does not** close (list stays interactive; prevents data loss) |
  1113→| **Click outside** | Modal scrim | Closes only if form is clean |
  1114→| **Click** | Column header | Cycle sort: asc → desc → default (the third click is the "unsort") |
  1115→| **Click** | Status tab | Filters list; keeps other filters; updates URL |
  1116→| **Click** | Same status tab again | No change (tabs are not toggles) |
  1117→| **Click** | Filter chip `×` | Removes that filter |
  1118→| **Click** | KPI tile | Drills to the target list with filters applied |
  1119→| **Click** | Alert pill | Opens its `fix` surface |
  1120→
  1121→### 3.2 Escape priority (one Esc closes one thing)
  1122→
  1123→1. Open popover or context menu
  1124→2. Top modal
  1125→3. Top drawer (dirty guard)
  1126→4. Selection
  1127→5. Search input focus
  1128→
  1129→### 3.3 Dirty guard
  1130→
  1131→Any close, replace, tab close, route change or browser back with `dirty = true` opens `DiscardChangesModal`: **Save · Discard · Keep editing**. Dirty = form values differ from the loaded record. Autosave drafts are for DocumentPage only.
  1132→
  1133→### 3.4 Surface stack rules
  1134→
  1135→- Max **depth 2**: base drawer + one child drawer opened from a picker `+ Add new`.
  1136→- Child save returns the created record into the parent field and focuses the next field. Child cancel returns focus to the picker.
  1137→- Opening a record from a list while a clean drawer is open **replaces** it. While dirty, guard first.
  1138→- **Make full page** promotes drawer state into DocumentPage without losing input.
  1139→- **Browser back** closes the top surface before navigating.
  1140→- **URL sync:** pages use the route; the top drawer is `?surface=party.drawer&id=123&mode=edit`; modals are not in the URL. Reload restores the drawer.
  1141→- Each **tab keeps its own stack**. Switching tabs does not close surfaces; closing a tab with dirty surfaces guards.
  1142→
  1143→### 3.5 Save, optimistic updates, undo
  1144→
  1145→| Action class | Strategy |
  1146→|---|---|
  1147→| Field edits, tags, status toggles, archive | Optimistic; rollback on error; **Undo toast 8 s** |
  1148→| Create | Wait for server id, then update list and return focus |
  1149→| Money movement, posting, sending, shipping, refunds | **Never optimistic.** Disable button, show progress, send `Idempotency-Key`, handle replay |
  1150→| Tier 3 edits | Preview first (`/preview-change`), then confirm |
  1151→| Tier 4 (posted/locked) | Fields read-only; menu shows Void / Adjust / Credit memo |
  1152→
  1153→### 3.6 Edit warnings (maps to section 1.9, rule 7)
  1154→
  1155→On entering edit: `GET /{type}/{id}/impact` → render `ExistingRecordBanner` by tier. On save: `PATCH` with `If-Match: version`. On `VERSION_CONFLICT`: show field diff (keep mine / keep theirs / merge). If `meta.lock` is set, show "Maria is editing this" banner and allow edit with warning.
  1156→
  1157→### 3.7 Keyboard (minimum)
  1158→
  1159→`⌘K` palette · `C` create menu · `/` focus search · `J/K` move row focus · `Enter` open · `X` toggle select · `E` edit · `Esc` per 3.2 · `⌘S` save · `⌘Enter` save and close.

  1163→## 4. API Contract
  1164→
  1165→### 4.1 Conventions
  1166→
  1167→| Topic | Rule |
  1168→|---|---|
  1169→| Base | `/api/v1`, JSON, auth via session or bearer |
  1170→| Resources | Plural nouns: `/parties`, `/items`, `/documents`, `/orders`, `/tickets`... |
  1171→| Documents | One family: `/documents?type=invoice`; type-specific rules come from `DocumentDef`, not separate routes |
  1172→| Actions | `POST /{resource}/{id}/{verb}` (send, void, ship, cancel, push) |
  1173→| Lists | `ListQuery` params; cursor pagination; response `meta.tabCounts` and `meta.summary` so tabs and footers need no extra call |
  1174→| Writes | `POST` create, `PATCH` partial update with `If-Match` |
  1175→| Idempotency | `Idempotency-Key` required on payments, refunds, sends, ships, posts, payroll |
  1176→| Errors | `ApiError` envelope with `code`, `fields`, `requestId` (`contracts.ts` section 10) |
  1177→| Permissions | Every record returns `meta.can` and `meta.maskedFields`; server enforces regardless |
  1178→| Soft delete | `DELETE` archives; hard delete only for drafts |
  1179→| Events | Every state change emits an event (`invoice.paid`, `order.shipped`, `ticket.sla_breached`) for automations, notifications and activity |
  1180→

  1227→### 4.4 Document Engine contract
  1228→
  1229→- `GET /document-defs` returns every `DocumentDef` (cache forever per deploy). The client builds Invoice, Bill, PO, Estimate, Credit memo from these configs.
  1230→- Totals are **server-computed**. The client may preview locally but always replaces with `DocumentTotals` from the save response.
  1231→- Status changes go through verbs (`/send`, `/void`, `/approve`), never by patching `status`. `INVALID_TRANSITION` is returned if illegal.
  1232→- `POST /documents/{id}/convert` handles Estimate → Invoice, Order → Invoice, Bill → Vendor credit and carries relations.

  1320→### 6.4 Lane interface rules (what keeps parallel work from colliding)
  1321→
  1322→- **Contracts first.** A lane never reads another lane's code; it reads `contracts.ts` and the endpoint map. Changes to a contract go through one owner and are announced to all lanes.
  1323→- **Config over code.** New screens are `ViewDef`, `DrawerDef` and `DocumentDef` entries; a lane only writes custom components for what the generic ones cannot express.
  1324→- **One registry.** Surface IDs, action codes and permission codes live in one registry (`platform_quick_action_registry` and `platform_permission_registry` on the data side); lanes add entries, they do not invent parallel lists.
  1325→- **Server decides.** Menus, create actions, field masks and `can` flags come from the API, so lanes do not each re-implement permission logic.
  1326→- **Seed data.** One shared seed (parties, items, accounts, orders, tickets) so every lane can test against realistic connected data from Day 2.

  1378→## 1. Findings that change how Settings gets built
  1379→
  1380→### 1.1 Roles and permissions
  1381→
  1382→1. **Two role columns, no roles table.** `tenant_memberships.role` allows exactly: `owner, admin, manager, staff, viewer, groomer, front_desk`. `user_tenants.role` allows: `platform_admin, tenant_admin, seller, staff, customer`. There is **no table of custom roles**.
  1383→2. **Permission check** is `platform_has_permission(tenant_id, permission_code)`. It returns true if `platform_is_admin()`, or if the caller's `crm_staff` row has a `platform_module_permissions` row for the permission's module (looked up in `platform_permission_registry`) with `access_level IN ('write','full')`.
  1384→3. `platform_module_permissions.access_level` is **unconstrained text**. Only `'write'` and `'full'` are read by any function in the files. No other value (for example `read`) is recognized anywhere.
  1385→4. `platform_module_permissions.staff_id` joins to **`crm_staff.id`**, not to a user id. A teammate needs a `crm_staff` row to hold module access.
  1386→5. **Field-level visibility is backed:** `platform_form_field_visibility(tenant_id, form_key, field_key, role_code, is_visible)`.
  1387→6. There is **no link** between `platform_quick_action_registry.action_code` (the Create menu registry) and `platform_permission_registry.permission_code`. The Create menu cannot be permission-filtered from data alone today.
  1388→
  1389→### 1.2 Row-level security (affects every Settings API)
  1390→
  1391→7. Two RLS patterns are in use: **(a)** `platform_is_tenant_member(tenant_id)` (any active member passes); **(b)** `tenant_id = current_setting('app.current_tenant_id')` on `acct_chart_of_accounts`, `acct_bank_transactions`, `acct_periods`, `platform_module_permissions`. Neither pattern checks a role or permission.
  1392→8. **RLS is enabled with zero policies** (deny-all for non-service-role clients) on: `tenant_settings`, `integration_keys`, `api_keys`, `policy_settings`, `app_settings`, `platform_feature_flags`. These tables are reachable only through a **server-side service-role API**. The Settings API must be server-side; the browser cannot query them directly.
  1393→9. `acct_workflows` and `acct_ap_approvals` have four policies each, all gated by membership only. Any active member could change approval rules at the database level; the API must enforce who can.
  1394→
  1395→### 1.3 Ledger integrity and audit
  1396→
  1397→10. `acct_audit_log` has `entry_hash` and `prev_hash` columns (hash-chain shape), but its policies allow **UPDATE and DELETE** to any tenant member.
  1398→11. The functions `acct_audit_row_change` and `acct_block_posted_mutation` exist, but **I found no `CREATE TRIGGER` that attaches them** in the uploaded files. They may be attached in the live DB; verify (query 6.1).
  1399→12. `acct_post_journal` checks tenant membership, book ownership and debit = credit. **I found no check that the target `acct_periods.status` is open.** `acct_periods.status` is plain text; the `acct_period_status` enum (`future, open, soft_closed, closed, locked`) exists but the column does not use it.
  1400→
  1401→### 1.4 Rules that have no storage
  1402→
  1403→13. **No bank rules table exists.** `acct_bank_transactions` has `match_status text NOT NULL` (no CHECK, values undefined) and **no category or account column**; the only link is `matched_journal_line_id`.
  1404→14. **No approval evaluation function exists.** `acct_workflows`, `acct_workflow_instances`, `acct_workflow_actions` and `acct_ap_approvals` are tables only. Something outside the database must route and advance approvals.
  1405→15. **No per-user or per-role spend/payment limit** is stored anywhere. `acct_workflows.threshold_amount` is the only amount field.
  1406→16. **No recurring bill/expense table.** Recurring exists for invoices (`acct_recurring_invoices`, plus a second pair `recurring_invoices` / `recurring_invoice_items`) and journals (`acct_recurring_journals`).
  1407→
  1408→### 1.5 Scatter
  1409→
  1410→17. **Four generic settings stores:** `tenant_settings(tenant_id, section, data jsonb)`, `policy_settings(tenant_id, scope, key, value text)`, `app_settings(key, value jsonb)` (**not tenant-scoped**), and `tenants.settings jsonb`. `tenant_settings.section` has no CHECK.
  1411→18. **Five tax structures:** `acct_tax_jurisdictions` + `acct_tax_codes` (effective dates, compound, recoverable %, payable/receivable accounts), `acct_tax_rates`, `acct_tax_rules` (**hard-coded default `state_code = 'TN'`**), `taxes` (simple), `commerce_sale_taxes`. No tax-category or tax-exempt column was found on `products`, `product_variants`, `orders`, `order_items` or `crm_customers`.
  1412→19. **Vendors live in four tables:** `acct_vendors`, `erp_vendors`, `vendors`, plus `suppliers` and `commerce_suppliers`. Customers: `crm_customers` (`customer_type`, `lifecycle_status`), `commerce_customer_accounts`, `portal_customer_accounts`. Products: `products` (canonical per hotfix E), `commerce_products`, `erp_products`, `commerce_catalog_items`. Orders: `orders`, `commerce_orders`, `erp_orders`. **The Party and Item entities in `contracts.ts` need an explicit mapping layer** (see section 4, G-14).
  1413→20. **Leftover vertical fields:** roles `groomer` and `front_desk`; feature-flag audience `vet`; `crm_settings` columns `vaccine_reminder_enabled`, `birthday_campaign_enabled`, `station_turnaround_buffer_minutes`; tables `jurisdiction_rules` (telemedicine) and `state_rules`. Do not surface these in Settings.

  1691→## 6. Verification Queries (run on the live database)
  1692→
  1693→```sql
  1694→-- 6.1 Are the audit and posted-entry guards actually attached?
  1695→select tgname, tgrelid::regclass as on_table, tgfoid::regproc as fn
  1696→from pg_trigger
  1697→where not tgisinternal
  1698→  and tgfoid::regproc::text in ('acct_audit_row_change','acct_block_posted_mutation');
  1699→
  1700→-- 6.2 Is there any bank-rule-like table I missed?
  1701→select table_name from information_schema.tables
  1702→where table_schema='public' and (table_name ilike '%bank%rule%' or table_name ilike '%categor%rule%');
  1703→
  1704→-- 6.3 Distinct access levels and registry modules in use
  1705→select access_level, count(*) from platform_module_permissions group by 1;
  1706→select module, count(*) from platform_permission_registry group by 1 order by 1;
  1707→
  1708→-- 6.4 Actual account types in use (settles D-2)
  1709→select account_type, subtype, count(*) from acct_chart_of_accounts group by 1,2 order by 1,2;
  1710→
  1711→-- 6.5 Which status set do bills use? (bill_status vs acct_document_status)
  1712→select column_name, udt_name from information_schema.columns
  1713→where table_schema='public' and table_name in ('acct_bills','bills','acct_vendor_bills')
  1714→  and column_name = 'status';
  1715→
  1716→-- 6.6 Which tax tables actually hold rows (settles D-6)
  1717→select 'acct_tax_codes' t, count(*) from acct_tax_codes
  1718→union all select 'acct_tax_rates', count(*) from acct_tax_rates
  1719→union all select 'acct_tax_rules', count(*) from acct_tax_rules
  1720→union all select 'taxes', count(*) from taxes;
  1721→
  1722→-- 6.7 Period status values in use and whether posting has ever hit a non-open period
  1723→select status, count(*) from acct_periods group by 1;
  1724→
  1725→-- 6.8 Which vendor/customer/product tables actually hold rows (settles G-14)
  1726→select 'acct_vendors' t, count(*) from acct_vendors
  1727→union all select 'erp_vendors', count(*) from erp_vendors
  1728→union all select 'vendors', count(*) from vendors
  1729→union all select 'crm_customers', count(*) from crm_customers
  1730→union all select 'products', count(*) from products
  1731→union all select 'commerce_products', count(*) from commerce_products
  1732→union all select 'erp_products', count(*) from erp_products;
  1733→```

  1754→## 1. Architecture
  1755→
  1756→```
  1757→AppShell
  1758→ ├─ TabBar (each tab = { route, surfaceStack[], envelope })
  1759→ ├─ SideNav (counts, pinned)
  1760→ ├─ GlobalSearch / CommandPalette
  1761→ ├─ CreateMenu (context-filtered)
  1762→ ├─ Routed content (module page: TableShell / DocumentEngine / Workspace / Studio)
  1763→ └─ SurfaceHost (renders the active tab's surface stack: drawer, modal, popover)
  1764→```
  1765→
  1766→**Three central stores** (everything else is local state):
  1767→
  1768→| Store | Holds | Key methods |
  1769→|---|---|---|
  1770→| `useSurfaces` | Per-tab surface stack, dirty flags | `open(request)`, `close(instanceId)`, `replace()`, `closeAll(tabId)`, `confirmDiscard()` |
  1771→| `useEnvelope` | Active tab's context envelope | `current()`, `derive(record)` returns the envelope for "Create from this" |
  1772→| `usePermissions` | Roles, field masks, feature flags | `can(action, record?)`, `isMasked(field)`, `flag(name)` |
  1773→
  1774→**Server state:** one query cache (React Query/SWR style), keyed `[entity, id]` and `[entity, 'list', normalizedQuery]`. Mutations invalidate by entity and by `relations` (so a payment refreshes the invoice, customer balance, bank feed and dashboard tile).
  1775→
  1776→**Rule: the server decides actions and permissions.** Menus, create menu and field masks come from the API (`/actions`, `/create-menu`, `meta.can`, `maskedFields`). The client never re-implements permission or state-machine logic. That is what keeps right-click menus identical everywhere.

  1889→### 3.2 Escape priority (one Esc closes one thing)
  1890→
  1891→1. Open popover or context menu
  1892→2. Top modal
  1893→3. Top drawer (dirty guard)
  1894→4. Selection
  1895→5. Search input focus

  1897→### 3.3 Dirty guard
  1898→
  1899→Any close, replace, tab close, route change or browser back with `dirty = true` opens `DiscardChangesModal`: **Save · Discard · Keep editing**. Dirty = form values differ from the loaded record. Autosave drafts are for DocumentPage only.
  1900→
  1901→### 3.4 Surface stack rules
  1902→
  1903→- Max **depth 2**: base drawer + one child drawer opened from a picker `+ Add new`.
  1904→- Child save returns the created record into the parent field and focuses the next field. Child cancel returns focus to the picker.
  1905→- Opening a record from a list while a clean drawer is open **replaces** it. While dirty, guard first.
  1906→- **Make full page** promotes drawer state into DocumentPage without losing input.
  1907→- **Browser back** closes the top surface before navigating.
  1908→- **URL sync:** pages use the route; the top drawer is `?surface=party.drawer&id=123&mode=edit`; modals are not in the URL. Reload restores the drawer.
  1909→- Each **tab keeps its own stack**. Switching tabs does not close surfaces; closing a tab with dirty surfaces guards.
  1910→
  1911→### 3.5 Save, optimistic updates, undo
  1912→
  1913→| Action class | Strategy |
  1914→|---|---|
  1915→| Field edits, tags, status toggles, archive | Optimistic; rollback on error; **Undo toast 8 s** |
  1916→| Create | Wait for server id, then update list and return focus |
  1917→| Money movement, posting, sending, shipping, refunds | **Never optimistic.** Disable button, show progress, send `Idempotency-Key`, handle replay |
  1918→| Tier 3 edits | Preview first (`/preview-change`), then confirm |
  1919→| Tier 4 (posted/locked) | Fields read-only; menu shows Void / Adjust / Credit memo |
  1920→
  1921→### 3.6 Edit warnings (maps to section 1.9, rule 7)
  1922→
  1923→On entering edit: `GET /{type}/{id}/impact` → render `ExistingRecordBanner` by tier. On save: `PATCH` with `If-Match: version`. On `VERSION_CONFLICT`: show field diff (keep mine / keep theirs / merge). If `meta.lock` is set, show "Maria is editing this" banner and allow edit with warning.
  1924→

  1926→

  1931→## 4. API Contract
  1932→
  1933→### 4.1 Conventions
  1934→
  1935→| Topic | Rule |
  1936→|---|---|
  1937→| Base | `/api/v1`, JSON, auth via session or bearer |
  1938→| Resources | Plural nouns: `/parties`, `/items`, `/documents`, `/orders`, `/tickets`... |
  1939→| Documents | One family: `/documents?type=invoice`; type-specific rules come from `DocumentDef`, not separate routes |
  1940→| Actions | `POST /{resource}/{id}/{verb}` (send, void, ship, cancel, push) |
  1941→| Lists | `ListQuery` params; cursor pagination; response `meta.tabCounts` and `meta.summary` so tabs and footers need no extra call |
  1942→| Writes | `POST` create, `PATCH` partial update with `If-Match` |
  1943→| Idempotency | `Idempotency-Key` required on payments, refunds, sends, ships, posts, payroll |
  1944→| Errors | `ApiError` envelope with `code`, `fields`, `requestId` (`contracts.ts` section 10) |
  1945→| Permissions | Every record returns `meta.can` and `meta.maskedFields`; server enforces regardless |
  1946→| Soft delete | `DELETE` archives; hard delete only for drafts |
  1947→| Events | Every state change emits an event (`invoice.paid`, `order.shipped`, `ticket.sla_breached`) for automations, notifications and activity |

  1995→### 4.4 Document Engine contract
  1996→
  1997→- `GET /document-defs` returns every `DocumentDef` (cache forever per deploy). The client builds Invoice, Bill, PO, Estimate, Credit memo from these configs.
  1998→- Totals are **server-computed**. The client may preview locally but always replaces with `DocumentTotals` from the save response.
  1999→- Status changes go through verbs (`/send`, `/void`, `/approve`), never by patching `status`. `INVALID_TRANSITION` is returned if illegal.
  2000→- `POST /documents/{id}/convert` handles Estimate → Invoice, Order → Invoice, Bill → Vendor credit and carries relations.
