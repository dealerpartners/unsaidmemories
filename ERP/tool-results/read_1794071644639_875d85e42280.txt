    36→## 1. Architecture
    37→
    38→```
    39→AppShell
    40→ ├─ TabBar (each tab = { route, surfaceStack[], envelope })
    41→ ├─ SideNav (counts, pinned)
    42→ ├─ GlobalSearch / CommandPalette
    43→ ├─ CreateMenu (context-filtered)
    44→ ├─ Routed content (module page: TableShell / DocumentEngine / Workspace / Studio)
    45→ └─ SurfaceHost (renders the active tab's surface stack: drawer, modal, popover)
    46→```
    47→
    48→**Three central stores** (everything else is local state):
    49→
    50→| Store | Holds | Key methods |
    51→|---|---|---|
    52→| `useSurfaces` | Per-tab surface stack, dirty flags | `open(request)`, `close(instanceId)`, `replace()`, `closeAll(tabId)`, `confirmDiscard()` |
    53→| `useEnvelope` | Active tab's context envelope | `current()`, `derive(record)` returns the envelope for "Create from this" |
    54→| `usePermissions` | Roles, field masks, feature flags | `can(action, record?)`, `isMasked(field)`, `flag(name)` |
    55→
    56→**Server state:** one query cache (React Query/SWR style), keyed `[entity, id]` and `[entity, 'list', normalizedQuery]`. Mutations invalidate by entity and by `relations` (so a payment refreshes the invoice, customer balance, bank feed and dashboard tile).
    57→
    58→**Rule: the server decides actions and permissions.** Menus, create menu and field masks come from the API (`/actions`, `/create-menu`, `meta.can`, `maskedFields`). The client never re-implements permission or state-machine logic. That is what keeps right-click menus identical everywhere.

   144→## 3. Interaction Contract (click and unclick)
   145→
   146→### 3.1 Gesture table
   147→
   148→| Gesture | Target | Behavior |
   149→|---|---|---|
   150→| **Click** | Row body (record list) | Open record in **drawer** (replaces current drawer; dirty guard first) |
   151→| **Click** | Row body (document list) | Navigate to **DocumentPage** |
   152→| **Click** | Row checkbox | Toggle selection only; never opens |
   153→| **Shift-click** | Checkbox | Range select |
   154→| **Click** | Header checkbox | Select all visible; banner offers "Select all N matching" |
   155→| **Click** | Empty table area / **Esc** | Clear selection (the "unclick") |
   156→| **Click** | Pill | `PeekPopover` opens; click again or outside closes |
   157→| **Hover** | Pill (desktop) | Peek after 300 ms intent delay; cancels on leave |
   158→| **⌘/Ctrl-click** | Pill or row | Open in new tab (new envelope from source) |
   159→| **Right-click** | Row | Context menu at cursor. If row is not selected, select **only** it. If row is within a selection, menu acts on the whole selection and shows bulk variants |
   160→| **Click** | Menu item | Runs `surface` or `request`; `confirm` shows `ConfirmDialog` first; menu closes |
   161→| **Click outside** | Menu / popover | Closes it |
   162→| **Click outside** | Drawer | **Does not** close (list stays interactive; prevents data loss) |
   163→| **Click outside** | Modal scrim | Closes only if form is clean |
   164→| **Click** | Column header | Cycle sort: asc → desc → default (the third click is the "unsort") |
   165→| **Click** | Status tab | Filters list; keeps other filters; updates URL |
   166→| **Click** | Same status tab again | No change (tabs are not toggles) |
   167→| **Click** | Filter chip `×` | Removes that filter |
   168→| **Click** | KPI tile | Drills to the target list with filters applied |
   169→| **Click** | Alert pill | Opens its `fix` surface |
   170→
   171→### 3.2 Escape priority (one Esc closes one thing)
   172→
   173→1. Open popover or context menu
   174→2. Top modal
   175→3. Top drawer (dirty guard)
   176→4. Selection
   177→5. Search input focus
   178→
   179→### 3.3 Dirty guard
   180→
   181→Any close, replace, tab close, route change or browser back with `dirty = true` opens `DiscardChangesModal`: **Save · Discard · Keep editing**. Dirty = form values differ from the loaded record. Autosave drafts are for DocumentPage only.
   182→
   183→### 3.4 Surface stack rules
   184→
   185→- Max **depth 2**: base drawer + one child drawer opened from a picker `+ Add new`.
   186→- Child save returns the created record into the parent field and focuses the next field. Child cancel returns focus to the picker.
   187→- Opening a record from a list while a clean drawer is open **replaces** it. While dirty, guard first.
   188→- **Make full page** promotes drawer state into DocumentPage without losing input.
   189→- **Browser back** closes the top surface before navigating.
   190→- **URL sync:** pages use the route; the top drawer is `?surface=party.drawer&id=123&mode=edit`; modals are not in the URL. Reload restores the drawer.
   191→- Each **tab keeps its own stack**. Switching tabs does not close surfaces; closing a tab with dirty surfaces guards.
   192→
   193→### 3.5 Save, optimistic updates, undo
   194→
   195→| Action class | Strategy |
   196→|---|---|
   197→| Field edits, tags, status toggles, archive | Optimistic; rollback on error; **Undo toast 8 s** |
   198→| Create | Wait for server id, then update list and return focus |
   199→| Money movement, posting, sending, shipping, refunds | **Never optimistic.** Disable button, show progress, send `Idempotency-Key`, handle replay |
   200→| Tier 3 edits | Preview first (`/preview-change`), then confirm |
   201→| Tier 4 (posted/locked) | Fields read-only; menu shows Void / Adjust / Credit memo |
   202→
   203→### 3.6 Edit warnings (maps to section 1.9, rule 7)
   204→
   205→On entering edit: `GET /{type}/{id}/impact` → render `ExistingRecordBanner` by tier. On save: `PATCH` with `If-Match: version`. On `VERSION_CONFLICT`: show field diff (keep mine / keep theirs / merge). If `meta.lock` is set, show "Maria is editing this" banner and allow edit with warning.
   206→
   207→### 3.7 Keyboard (minimum)
   208→
   209→`⌘K` palette · `C` create menu · `/` focus search · `J/K` move row focus · `Enter` open · `X` toggle select · `E` edit · `Esc` per 3.2 · `⌘S` save · `⌘Enter` save and close.

   213→## 4. API Contract
   214→
   215→### 4.1 Conventions
   216→
   217→| Topic | Rule |
   218→|---|---|
   219→| Base | `/api/v1`, JSON, auth via session or bearer |
   220→| Resources | Plural nouns: `/parties`, `/items`, `/documents`, `/orders`, `/tickets`... |
   221→| Documents | One family: `/documents?type=invoice`; type-specific rules come from `DocumentDef`, not separate routes |
   222→| Actions | `POST /{resource}/{id}/{verb}` (send, void, ship, cancel, push) |
   223→| Lists | `ListQuery` params; cursor pagination; response `meta.tabCounts` and `meta.summary` so tabs and footers need no extra call |
   224→| Writes | `POST` create, `PATCH` partial update with `If-Match` |
   225→| Idempotency | `Idempotency-Key` required on payments, refunds, sends, ships, posts, payroll |
   226→| Errors | `ApiError` envelope with `code`, `fields`, `requestId` (`contracts.ts` section 10) |
   227→| Permissions | Every record returns `meta.can` and `meta.maskedFields`; server enforces regardless |
   228→| Soft delete | `DELETE` archives; hard delete only for drafts |
   229→| Events | Every state change emits an event (`invoice.paid`, `order.shipped`, `ticket.sla_breached`) for automations, notifications and activity |
   230→
   231→### 4.2 Cross-cutting endpoints (build once, used by every module)
   232→
   233→| Endpoint | Returns | Used by |
   234→|---|---|---|
   235→| `GET /search?q&types&scope` | `SearchResponse` | Palette, pickers, scoped-to-global search |
   236→| `GET /create-menu?module&tab&record` | `CreateAction[]` | CreateMenu |
   237→| `GET /{type}/{id}/actions?surface` | `MenuAction[]` | Context menu, row `⋯`, headers |
   238→| `GET /peek/{type}/{id}` | `PeekCard` | Pill popovers |
   239→| `GET /{type}/{id}/activity` | `ActivityEntry[]` | ActivityTimeline |
   240→| `GET /{type}/{id}/impact` | `ImpactSummary` | ExistingRecordBanner |
   241→| `POST /{type}/{id}/preview-change` | `ChangePreview` | ChangeImpactModal |
   242→| `POST /{type}/{id}/push` | `PushResult` | PushToGlobalModal |
   243→| `POST /bulk/{type}` | `BulkResult` | BulkBar |
   244→| `GET /nav-counts` | counts by nav key | SideNav badges |
   245→| `GET /dashboard/tiles` | tile values with drill queries | Dashboard |
   246→| `POST /import/jobs` + `/commit` + `/undo` | `ImportJob` | Import hub |
   247→| `POST /export` | job id, then file | Export buttons |
   248→| `POST /files` | `{ id, url }` | AttachmentStrip |
   249→
   250→### 4.3 Resource map by module
   251→
   252→| Module | List / read | Create / update | Key actions |
   253→|---|---|---|---|
   254→| **Parties** | `GET /parties` (role, segment filters), `/parties/{id}` | `POST/PATCH /parties` | `/archive`, `/roles` (add/remove), `/push`, `/merge` |
   255→| **Items** | `GET /items`, `/items/{id}` | `POST/PATCH /items` | `/publish`, `/reprice`, `/archive`, `/push` |
   256→| **Categories / Collections** | `GET /categories`, `/collections` | `POST/PATCH` | n/a |
   257→| **Documents** | `GET /documents?type=` | `POST/PATCH /documents` | `/send`, `/remind`, `/void`, `/convert`, `/duplicate`, `/pdf`, `/journal-entry` |
   258→| **Payments** | `GET /payments` | `POST /payments` (apply to many) | `/void` |
   259→| **Bills** | `GET /documents?type=bill` | same | `POST /bills/pay` (PayBillsRequest), `/approve`, `/match` |
   260→| **Bank transactions** | `GET /bank-transactions` | n/a (feed) | `/match`, `/categorize`, `/create-from` (expense, transfer, deposit), `/exclude`, `POST /rules` |
   261→| **Reconcile** | `GET /reconciliations/{id}` | `POST /reconciliations` (setup) | `/toggle-line`, `/finish` |
   262→| **Accounts** | `GET /accounts`, `/accounts/{id}/register` | `POST/PATCH` | `/merge`, `/deactivate` |
   263→| **Orders** | `GET /orders`, `/orders/{id}` | `POST /orders` (sales order) | `/ship`, `/labels`, `/cancel`, `/sync-tracking`, `/issues`, `POST /orders/batch-labels` |
   264→| **Refunds / Returns** | `GET /returns` | `POST /returns`, `POST /refunds` | `/decision`, `/receive` |
   265→| **Purchasing** | `GET /documents?type=purchase_order` | same | `/send`, `/receive` (items), `/create-bill` |
   266→| **Inventory** | `GET /inventory`, `/inventory/{itemId}/history` | n/a | `POST /inventory/adjustments`, `/transfers` |
   267→| **Designs / Studio** | `GET /designs`, `/collections` | `POST/PATCH` | `/publish` (creates Items), `/duplicate` |
   268→| **Marketing** | `GET /discounts`, `/banners`, `/popups`, `/posts`, `/campaigns` | `POST/PATCH` | `/pause`, `/schedule`, `/publish` |
   269→| **Support** | `GET /tickets`, `/tickets/{id}/messages` | `POST /tickets`, `POST /tickets/{id}/messages` | `/assign`, `/merge`, `/status`, `/macro` |
   270→| **Tasks** | `GET /tasks` | `POST/PATCH` | `/complete` |
   271→| **Contractors** | `GET /parties?role=contractor` | same | `/w9-invite` |
   272→| **Reports** | `GET /reports/{key}` | n/a | `/schedule`, `/save-view`; rows include `drill` query |
   273→| **Settings** | per page: `/settings/{section}` | `PATCH` | Roles, approvals, bank rules, recurring templates |
   274→
   275→**Workspace endpoints** return a draft the client edits: `POST /bills/pay/draft`, `POST /payments/receive/draft`, `POST /reconciliations`. Finish calls the real action with an idempotency key.
   276→
   277→### 4.4 Document Engine contract
   278→
   279→- `GET /document-defs` returns every `DocumentDef` (cache forever per deploy). The client builds Invoice, Bill, PO, Estimate, Credit memo from these configs.
   280→- Totals are **server-computed**. The client may preview locally but always replaces with `DocumentTotals` from the save response.
   281→- Status changes go through verbs (`/send`, `/void`, `/approve`), never by patching `status`. `INVALID_TRANSITION` is returned if illegal.
   282→- `POST /documents/{id}/convert` handles Estimate → Invoice, Order → Invoice, Bill → Vendor credit and carries relations.

   375→### 1.1 The five shared entities
   376→
   377→Everything in the Create Actions list collapses into five entity families. This is what makes the platform feel integrated: modules are *views* over shared entities, not separate databases.
   378→
   379→| Entity | What it is | Roles / Types | Used by |
   380→|---|---|---|---|
   381→| **Party** | One person/company record | Customer, Vendor, Supplier, Contractor, Seller, Lead (a party can hold many roles) | Sales, Expenses, CRM, Orders, Support, Tax (1099), Marketplace |
   382→| **Item** | Anything sellable/buyable | Product, Service, Blank, Bundle, Design-linked product, Gift card, Subscription | Catalog, Studio, Invoices, Bills, PO, Orders, Inventory, Channels |
   383→| **Document** | Any multi-line transaction | Invoice, Estimate, Sales order, Sales receipt, Credit memo, Bill, Expense, Check, PO, Vendor credit, RMA, Journal entry | Sales, Expenses, Orders, Purchasing, Returns, Accounting |
   384→| **Money movement** | Cash actually moving | Payment, Payment link, Deposit, Transfer, Settlement/Payout, Refund | Sales, Bills, Banking, Reconcile, Stripe/Shopify |
   385→| **Account** | Ledger node | Chart of Accounts, Bank, Credit card, Loan, Line of credit | Accounting, every Document line, Reconcile, Tax, Reports |

   387→**Rule:** "Add vendor" and "Add supplier" and "Add customer" are the **same drawer** (Party drawer) with a different default role pill. Same for "Add contractor" (role = Contractor, plus W-9 invite section). Never build four forms.

Invoice, Bill, PO, Sales order, Estimate, Credit memo, Vendor credit differ only by *config* (party role, line columns, status machine, posting rules). Build once.

   392→
   393→| Surface | Use when | Examples | Escape hatch |

   405→### 1.3 The Context Envelope (this is the integration engine)
   406→
   407→Every surface carries an invisible envelope. Creating something from inside a record **prefills from that record**; creating from the global Create menu inherits only the **active tab's** envelope.
   408→
   409→```
   410→envelope = {
   411→  origin_module, origin_record_id, origin_tab_id,
   412→  party_id, order_id, item_id, design_id, account_id,
   413→  channel_id, currency, date_range, return_to
   414→}
   415→```
   416→
   417→Examples:
   418→- On **Order #1042** → Create → Invoice: party, lines, channel, and `order_id` are prefilled and linked.
   419→- On **Vendor: Printful** → Create → Bill: vendor, terms, default expense category prefilled; open POs from that vendor show as a "Match PO" suggestion.

   421→- On **Bank transaction** (Reconcile) → Create → Expense: amount, date, paid-from prefilled; "Match" and "Create" are siblings.
   422→
   423→`return_to` means closing any drawer/modal/page returns to the exact scroll position and tab it came from.

   499→### 1.9 Scoped Workspaces → Global Hubs (the Push pattern)
   500→
   501→Catalog, Contacts/CRM, Support and Marketing each exist **twice on purpose**: once as a **scoped view** inside the area where the work happens, and once as the **global hub** that is the system of record. This is how a user never has to leave what they're doing to get or create what they need.
   502→
   503→| Scoped view (where you work) | Lives in | Global hub (system of record) | Push action | Pull action |
   504→|---|---|---|---|---|
   505→| **My Catalog** | Design Studio / My products | **Global Catalog** | **Publish** | Add a blank/product from global into My Catalog |
   506→| **Contacts** | Finance (Sales, Expenses, Accounting) | **Global Contacts / CRM** | **Create and push** | **Search global → Use here** |
   507→| **Support** | Record context (Orders, Sales, Customers) | **Global Support** (Inbox & Tickets) | Create ticket here → lands in global queue | Link an existing global ticket |
   508→| **Marketing** | Studio / Catalog / Product context | **Global Marketing** | Promote here → lands in global calendar/queue | Pull from global library/campaigns |
   509→
   510→**Why two:** The designer cannot bounce to the global catalog mid-design. The user in Finance should not have to open CRM to bill someone. Scoped = fast, in context, only what you need. Global = governed, searchable, shared across the whole platform.
   511→
   512→**Rules**
   513→
   514→1. **One record identity.** A scoped view is a lens (or staging copy) linked to a single global ID. Pushing never makes a second record.
   515→2. **Two entry flows, same destination.**
   516→   - *Create → push:* new contact/product made in scope, then promoted to global.
   517→   - *Search → link:* user searches the global hub from the scoped view and attaches the existing record. Search always runs **before** create ("Does this already exist?").
   518→3. **Dedupe on push.** Match keys: Contact = email / tax ID / name + address; Product = SKU / design ID; Ticket = requester + related record. On a match the push modal offers **Link to existing · Merge · Create anyway**.
   519→4. **State pill on every scoped row:** `Local only` → `Pushed` → `Live/Global`. Catalog adds `Draft → Published → Syncing to channels`.
   520→5. **Provenance:** global records carry a source pill (`Created in Studio`, `Created in Finance`) so context is never lost after the push.
   521→6. **Visibility:** a scoped item is visible to the creator/team until pushed; global visibility follows Roles & permissions. Pushing is its own permission (e.g. Publish to catalog).
   522→7. **Edit from either view, with an "existing record" warning.** The user is never sent to the other view to make a change. Because there is only one record underneath (rule 1), an edit made in the scoped view or the global hub writes to the same record and shows up in both immediately. The safeguard is a warning on entering edit, not a redirect.
   523→
   524→   **Warning tiers (shown when edit opens, in the drawer/page header):**
   525→
   526→   | Tier | Applies to | What the user sees |
   527→   |---|---|---|
   528→   | **1 — Notice** | Local only / not yet pushed | No warning needed |
   529→   | **2 — Existing record banner** | Pushed/Global record, edited from anywhere | Banner: *"You're editing an existing record shared with Global Catalog."* + impact line (e.g. *Used in 14 products · 3 open invoices · 2 channels*) + **View where used**. Non-blocking. |
   530→   | **3 — Confirm on save** | Edit changes a field with downstream effect (price, SKU, email, tax ID, terms, default account) | Save opens a small modal with a before → after summary of what propagates; options **Save** · **Save and apply to open drafts** · Cancel |
   531→   | **4 — Locked** | Posted financial documents, reconciled transactions | Fields locked; offer **Void**, **Adjust**, or **Create credit memo** instead of edit |
   532→
   533→   **Safeguards that make edit-anywhere safe:**
   534→   - **Source pill in the activity log:** every edit records *edited from My Catalog / Studio / Finance / Global*, who, and the before → after values.
   535→   - **Concurrency:** soft lock banner (*"Maria is editing this"*) and a version check on save; on conflict show a field-level diff to keep mine, keep theirs, or merge.
   536→   - **Permissions still apply:** edit rights follow Roles and permissions; fields like cost, margin and bank details stay masked and read-only without the right role.
   537→   - **Undo:** a toast with **Undo** after save for Tier 2 edits, plus Activity → Restore previous value.
   538→   - **Same warning component everywhere:** one Existing Record Banner component, parameterized by record type and impact counts, used by Party, Item, Ticket, Campaign and Account drawers.
   539→8. **Create menu:** actions in a scoped context default to creating locally with **Push to global** pre-checked in the drawer footer (`Save` · `Save and push`).

  1041→## PART 3.5 — Domain Structure & the Undefined Modules
  1042→
  1043→### A. The test: standalone module, sub-area, or setting?
  1044→
  1045→A thing earns its own **standalone module** only if it passes at least 4 of 5:
  1046→
  1047→1. Own primary entity with its own lifecycle
  1048→2. Own list view people live in
  1049→3. Own permission role (someone's job is this)
  1050→4. Used by 3+ other modules
  1051→5. Own ledger or compliance impact
  1052→
  1053→Otherwise it is a **sub-area** of a domain parent, or an **engine/setting** that other screens call.
  1054→
  1055→| Candidate | Entity | Own list | Own role | Used by | Ledger/compliance | Verdict |
  1056→|---|---|---|---|---|---|---|
  1057→| **Inventory** | Stock record + stock ledger | Yes | Warehouse/ops | Catalog, Orders, PO, Returns, Sales | Asset + COGS | **Standalone page** under Operations |
  1058→| **Payroll** | Employee, Pay run, Pay stub | Yes | Payroll admin (restricted) | Accounting, Tax, Time, Reports | Heavy | **Standalone page** under People |
  1059→| **Time** | Time entry | Weekly grid only | No | Payroll, Invoices, Tasks | Indirect | **Collapse** into People (feature, not a module) |
  1060→| **Sales tax** | Rate, jurisdiction, filing | Filings only | Finance | Invoices, Orders, Items, Parties, Reports | Liability account | **Engine in Settings** + sub-area of Business Tax |
  1061→
  1062→### B. Catalog vs Inventory vs POD (the fix)
  1063→
  1064→Catalog, Inventory and Purchasing are three layers over the same Item, not three competing modules.
  1065→
  1066→| Layer | Question it answers | Owns |
  1067→|---|---|---|
  1068→| **Catalog** | *What is this and where is it sold?* | Definition, price, variants, **designs**, blanks, supplier link, channels, publish state |
  1069→| **Inventory** | *What do I physically have?* | On hand, reserved, available, locations, cost layers, counts, transfers, adjustments, stock history |
  1070→| **Purchasing** | *How does supply arrive?* | Purchase orders, receiving, supplier cost |
  1071→
  1072→Every Item gets a **Fulfillment type**, set in the Item drawer. It decides which tabs, pills and PO behavior the item has:
  1073→
  1074→| Fulfillment type | Example | Tracks stock? | Availability comes from | PO type | Pill |
  1075→|---|---|---|---|---|---|
  1076→| **Stock** | In-house goods, wholesale | **Yes** | Inventory on-hand | **Replenishment PO** (manual or reorder-point) | `42 in stock` |
  1077→| **POD (print on demand)** | Design on a blank | No | Supplier / blank availability | **Fulfillment PO**, auto-created per order | `Made on demand` |
  1078→| **Supplier-fulfilled (dropship)** | Supplier ships direct | No | Supplier feed | **Fulfillment PO**, auto-created per order | `Ships from supplier` |
  1079→| **Digital / Service** | Download, hourly service | No | Always available | None | none |
  1080→| **Bundle** | Tee + hat set | Derived | Lowest component availability | Per component | `Bundle` |
  1081→
  1082→**Consequences**
  1083→- **Catalog owns POD completely:** Design → Product → Blank → Supplier. A POD product has no stock number, so the Inventory tab, Adjust stock and Cycle count never appear for it.
  1084→- **Inventory is only for real stock.** Its list shows only items with *Track inventory = on*.
  1085→- **Two PO types.** Replenishment PO is a manual or reorder-triggered buy for stock. Fulfillment PO is generated from an Order line and is linked to that order. Same Document Engine, different config.
  1086→- **Blanks:** if the supplier holds them, a Blank is a Catalog record with supplier availability. If *you* buy and hold blanks (in-house printing), the Blank becomes an Inventory item (raw material), which later needs a simple production/BOM step. Flag this as a future decision.
  1087→- **The stock pill on a product row** is replaced by the fulfillment pill for POD items.
  1088→
  1089→### C. Recommended domain parents
  1090→
  1091→Each parent is a nav group containing sub-areas. Each sub-area keeps its own list and Create actions.
  1092→
  1093→| Domain parent | Contains |
  1094→|---|---|
  1095→| **Finance** | Accounting · Sales · Expenses & Bills · **Business Tax** (Income tax · **Sales tax** · **Payroll tax** · 1099s) |
  1096→| **People** | **Employees** · Contractors · **Time** · **Payroll** |
  1097→| **Operations** | Orders · Fulfillment · Purchasing · **Inventory** · Returns · Shipping |
  1098→| **Commerce** (Catalog & Design) | Studio + My Catalog → Global Catalog · Channels |
  1099→| **Growth** | CRM · Marketing · Social · Ads |
  1100→| **Support** | Inbox & Tickets · Queues · SLA · Trust & Safety |
  1101→| **Reports / Settings** | Unchanged |
  1102→
  1103→Notes on the moves:
  1104→- **Contractors** are a People sub-area *and* keep a scoped view inside Expenses & Bills that pushes to People, the same pattern as section 1.9.
  1105→- **Employees** are a Party role, so they use the same Party drawer with Pay, Tax and Bank sections (masked and restricted).
  1106→- **Sales tax and Payroll tax** live under Business Tax because they are filings and liabilities, while the *engines* that feed them live elsewhere (Settings and Payroll).
  1107→
  1108→### D. Definitions for the four
  1109→
  1110→**Payroll** (People)
  1111→- Entities: Employee (Party role), Pay schedule, Pay run, Pay stub, Tax forms (W-2, 941).
  1112→- **Add employee:** Party drawer with Pay (salary/hourly, schedule), Tax (W-4, state), Bank (direct deposit), and an onboarding invite.
  1113→- **Run payroll:** Workspace. Period → hours/salary (hours pulled from Time) → review gross / deductions / taxes / net → approve → pay.
  1114→- Pay run list columns: Period · Pay date · Employees · Gross · Taxes · Net · Status pill (Draft / Approved / Paid) · ⋯
  1115→- Posts journal entries automatically (wages expense, tax liabilities, bank). Rides along into Business Tax → Payroll tax and Reports.
  1116→- **Decision to make:** build vs integrate. Payroll is compliance-heavy (filings, multi-state tax). Define the entity, surfaces and ledger posting now, and consider a provider integration behind the same screens.
  1117→
  1118→**Time** (People)
  1119→- **Time entry:** modal or weekly grid. Fields: Person, Date, Hours, Related (Customer / Task / Order), Billable toggle, Rate, Note.
  1120→- Rides along: Invoice has **Add billable time** on its line picker; Payroll pulls approved hours; Tasks can start a timer.
  1121→
  1122→**Sales tax** (Business Tax + Settings engine)
  1123→- **Engine (Settings):** Rates and jurisdictions, tax categories, nexus rules.
  1124→- **Item drawer:** Tax category field. **Party drawer:** Tax exempt toggle + certificate upload.
  1125→- **Document Engine:** per-line tax calculation and a tax summary in the totals block.
  1126→- **Business Tax → Sales tax:** liability by jurisdiction · Filing periods · **Pay sales tax** (workspace, like Pay bills) · Nexus alert pills.
  1127→- Orders from channels arrive with marketplace-collected tax flagged, so it is excluded from your liability.
  1128→
  1129→**Inventory** (Operations)
  1130→- Defined in Module: Purchasing & Inventory, now restricted to *Stock* items. Add: **Locations** (warehouses/bins) and a **Stock ledger** (every movement with source pill: PO receipt, order, adjustment, transfer, return).

  1134→## PART 3.6 — POS, Gift Cards, Banking & Cards
  1135→
  1136→### A. POS (brick-and-mortar)
  1137→
  1138→**Principle:** POS is a **channel + a device surface**, not a separate system. A store sale is a normal Order/Sales receipt with a store channel pill, so Inventory, Accounting, CRM, Returns and Support all work unchanged.
  1139→
  1140→**Entities:** Location (store) · Register · Shift (drawer session) · Sale · Tender (card, cash, gift card, split) · Receipt · Hardware (reader, receipt printer, cash drawer, scanner)
  1141→
  1142→| Surface | Type | Contents |
  1143→|---|---|---|
  1144→| **POS app** | Full-screen, touch-first, offline-capable | Product grid + search + barcode scan → cart → attach customer (Party picker, optional, with `+ Add`) → discounts → tender → receipt (print/email/SMS) |
  1145→| Open shift | Modal | Register, starting cash |
  1146→| Close shift | Modal → count sheet | Counted cash vs expected, over/short, card totals, tips, **Z report** |
  1147→| Cash in / out | Modal | Amount, reason (paid-out, petty cash) |
  1148→| Park / resume sale | Inline | Held carts per register |
  1149→| Refund / exchange | Modal | Scan or search receipt, select lines, restock toggle, refund to original tender or store credit |
  1150→| Redeem / sell gift card | Modal | See 3.6 B |
  1151→| Manager override | PIN modal | Required for discounts above threshold, voids, refunds, price override |
  1152→
  1153→**Back-office views:** Locations list (Name · Address · Registers · Open shift pill · Today's sales · Stock alerts) · Shifts list (Register · Cashier · Opened · Closed · Expected · Counted · Variance pill) · POS sales appear in Orders and Sales with a **Channel pill** `Store: Downtown`.
  1154→
  1155→**Rides along**
  1156→- **Inventory:** stock is tracked per location; sales decrement the selling location; transfers between stores and warehouse; optional buy-online-pickup-in-store.
  1157→- **POD items in store:** sold as an *order for later* (ship or pickup), never as instant stock.
  1158→- **Accounting:** Z report posts a journal entry (sales by tender, tax, tips, cash over/short, gift card liability); card settlement reconciles to payouts in Bank transactions.
  1159→- **Sales tax:** location-based rates and exemptions.
  1160→- **CRM:** attached customer gets the sale on their profile; walk-up sales stay anonymous.
  1161→- **Support:** receipt lookup creates a ticket or RMA with the sale pre-linked.
  1162→- **Permissions:** Cashier, Shift lead, Manager roles; override rules live in Settings → Approvals and limits.
  1163→- **Offline mode:** queue sales and card-present fallbacks, sync on reconnect, and define oversell conflict rules before launch.
  1164→
  1165→### B. Gift cards
  1166→
  1167→**Treat gift cards as your own ledger entity.** A gift card sale is a **liability**, not revenue; revenue is recognized when the card is redeemed.
  1168→
  1169→**Entities:** Gift card (code, initial value, balance, currency, issued to, expiry, status) · Gift card transaction (issue, redeem, reload, refund, adjust, expire)
  1170→
  1171→| Action | Surface | Notes |
  1172→|---|---|---|
  1173→| Sell gift card | Item type = Gift card (digital or physical) | Sold online, in POS, or on an invoice; card is created on payment |
  1174→| Issue manually | **Drawer** | Amount, recipient, message, delivery (email / print), expiry |
  1175→| Check balance | Popover / modal | Enter or scan code |
  1176→| Redeem | Tender at checkout (online + POS) | Supports partial redemption and split tender |
  1177→| Reload / Adjust / Disable | Modal | Reason required, logged |
  1178→| Refund to gift card | Option in Refund modal | Or to store credit |
  1179→
  1180→**List columns:** ☐ · Code (masked) · Recipient · Purchaser (pill) · Issued · Initial · Balance · Expires · Status pill (Active / Partially used / Redeemed / Expired / Disabled) · Source (Online / Store / Manual) · ⋯
  1181→**Right-click:** Open · Email card · Print · Reload · Adjust · **Create from this ▸** Ticket · Note · Disable
  1182→**Detail:** Ledger of every movement with source pill (Order #, Register, Manual).
  1183→**Accounting:** Gift card liability account; unredeemed-balance reports. Expiry, breakage and unclaimed-property rules vary by jurisdiction, so have a lawyer or accountant set the policy.
  1184→**Store credit** (from credit memos and returns) uses the same ledger with a different type.
  1185→
  1186→### C. Banking & Cards (Stripe Connect + Treasury + Issuing)
  1187→
  1188→**Model:** Merchants are Connect connected accounts. Treasury for platforms provides a financial account per merchant; Issuing provides debit cards drawn on that account. Payouts from Stripe settle into the financial account.
  1189→
  1190→**Surfaces (Finance → Banking, merchant-facing)**
  1191→
  1192→| Surface | Type | Contents |
  1193→|---|---|---|
  1194→| Financial account | Page | Balance, available, pending, recent movement |
  1195→| Move money | Modal | Transfer to / from linked bank, ACH out, payout sweep rules |
  1196→| Cards list | List | Card · Holder (Party/Team pill) · Virtual/Physical · Status · Limit · Spent this period · ⋯ |
  1197→| Issue card | **Drawer** | Holder, type, spend limit, allowed merchant categories, shipping, approval rules |
  1198→| Card transactions | Feed in Bank transactions | Auto-create **Expense** with receipt-capture prompt; match to Bill; categorize via Rules |
  1199→| Pay bills from financial account | Option in Pay bills workspace | Uses ACH details on the Vendor |
  1200→| Onboarding / KYC-KYB | Drawer or embedded component | Collect and verify business info before enabling Banking |
  1201→
  1202→**Rides along:** Card spend limits tie to **Approvals and limits** · Settlement posts payouts into the financial account · Reconcile treats the financial account as a bank · Expenses and Business tax read card spend.
  1203→
  1204→**Compliance surfaces you must design (they land in Support):** a regulated **Complaints and Disputes queue** with recordkeeping, plus disclosures and customer-service access inside the Banking UI.

  1217→| **Seller** | Marketplace sellers | Onboarding, payouts, listing issues, compliance |
  1218→| **Attention** | Anyone | SLA at risk, escalated, manual-push failures |
  1219→| **Disputes and Complaints** | Buyers and merchants | Payment disputes/chargebacks (links to Sales → Disputes) and regulated Banking/Card complaints |
  1220→| **Internal** (optional) | Your team | Platform bugs, requests |
  1221→
  1222→### B. Ticket model
  1223→
  1224→**Ticket type** drives fields, sidebar cards and available actions: Question · Order issue · Return · Payment / dispute · Billing · Complaint · Seller onboarding · Bug.
  1225→**Fields:** Subject · Requester (Party pill) · Type · Channel · Priority · Status (New / Open / Pending / On hold / Solved / Closed) · Assignee · Queue · Tags · **Related records** (Order, Invoice, RMA, Product, Design, Shipment, Gift card).
  1226→
  1227→### C. Ticket workspace (three panes)
  1228→
  1229→| Pane | Contents |
  1230→|---|---|
  1231→| **List** | Views: My tickets · Unassigned · Attention · SLA at risk · By queue. Columns: ☐ · Ticket # · Subject · Requester · Type pill · Channel pill · Priority · Status · Assignee · **SLA timer pill** · Related pills · Updated |

  1233→| **Context sidebar** | Cards: **Customer** (LTV, balance, segment) · **Recent orders** (inline: Refund…, Track shipment, Resend, Cancel) · **Open invoices** (Record payment, Send) · **RMA** (Approve/Decline) · **Design proof** for POD items · **Shipment tracking** · **Previous tickets** · Notes |
  1234→
  1235→**Right-click on a ticket:** Assign · Change status · Change priority · Merge · Link record · **Create from this ▸** RMA · Credit memo · Refund · Task · Vendor credit (supplier defect) · Add note · Close.
  1236→**Bulk:** Assign · Merge · Tag · Apply macro · Close.
  1237→
  1238→### D. Inbound sources and automation
  1239→
  1240→- **Sources:** email, chat, social DMs, marketplace messages (Etsy, Amazon, etc.), web forms, **Report a problem… on an order**, POS receipt lookup, Banking complaint form.
  1241→- **Automation (trigger → condition → action):** *Trigger:* ticket created, RMA created, payment failed, order delayed, SLA warning. *Action:* assign, route to queue, set priority, tag, auto-reply, create task, notify.
  1242→- **Macros** with merge fields (customer, order, tracking).
  1243→- **SLA policies:** first response and resolution targets by queue, priority and customer tier; timers pause on Pending; respects Office hours; breach raises an Alert pill and a task.
  1244→
  1245→### E. Self-service and knowledge
  1246→
  1247→- **Help center / customer portal:** order status, tracking, self-serve returns (creates an RMA), past tickets, gift card balance. This is the deflection layer.
  1248→- **Knowledge base:** articles, docs, policies; suggested in the composer and on the contact form; **Create article from ticket**; article feedback.
  1249→- **CSAT:** survey on solve; QA review sampling.
  1250→
  1251→### F. Feedback loops into the rest of the platform
  1252→
  1253→| Signal | Lands in |
  1254→|---|---|
  1255→| High issue or return rate per product | Catalog **alert pill** on the product + task |
  1256→| Supplier defect | Vendor credit / supplier claim |
  1257→| Fulfillment failures | Orders → Needs attention |
  1258→| Seller problems | Seller detail + Onboarding queue |
  1259→| Complaint volume by reason | Reports → Support (reason, first response, resolution, backlog, CSAT) |
  1260→
  1261→**Permissions:** Agent, Lead, Admin. Sensitive fields (card, bank, tax IDs) masked in conversations. Regulated complaints and disputes are retained with full audit history.

  1265→## PART 4 — Conflicts & Decisions to Notate
  1266→
  1267→1. **Scoped vs global trees are intentional, not duplicates.** My Catalog (Studio) → Global Catalog, Contacts (Finance) → Global Contacts/CRM, plus scoped Support and Marketing, follow the Push pattern in section 1.9. Edits are allowed from either view, with the existing-record warning (rule 7 in section 1.9). Still open: the dedupe keys, which role can push, and whether Orders is also scoped, since it appeared in both places.
  1268→
  1269→2. ** User manually set Sales tax in settings since Invoices, Orders and Tax all depend on it. Payroll ia a native build Blanks are a seetings prefernce on whether a user holds them or supplier holds them.
  1270→
  1271→3. **Product catalog prerequisite** (Department / Sub-department / Service type / SKU line). Make it inline-creatable so it never blocks entry; otherwise users will bounce.
  1272→
  1273→4. **Vendor vs Supplier vs Seller.**  **Vendor** = you pay them for operating costs; **Supplier** = fulfills your products (feeds PO, blanks, integrations); **Seller** = marketplace participant who sells through you. All Party roles, different drawer sections.
  1274→
  1275→5. **Order vs Sales order vs Invoice.** Order is the commerce record (from channels); Sales order is manual order entry that becomes an Order; Invoice is the billing doc generated from either. Link all three with relation pills.
  1276→
  1277→6. **Statement ≠ Statement (bank).** Customer Statement (billing summary) and Reconcile "statement ending balance" use the same word. Label the latter "Bank statement."
  1278→
  1279→7. **Void vs Delete vs Archive.** Posted documents: **Void** only (keeps audit trail). Drafts: Delete. Parties/Items/Accounts: Archive.
